PiLog is an Electron + React + TypeScript desktop app. The main process owns truth (DB, secrets, GitHub, Pi runtime, file system); the renderer is a UI client that only talks to main through a typed IPC contract. These standards exist to keep that boundary honest and the code refactor-safe.

## Style

- TypeScript everywhere. No `.js` source files outside config.
- `camelCase` for variables/functions, `PascalCase` for types/components/classes, `SCREAMING_SNAKE_CASE` for module-level constants and IPC channel names.
- **Named exports only.** No `export default` except where a framework requires it (e.g. Vite config, Electron entry).
- Imports use path aliases (`@main/*`, `@preload/*`, `@renderer/*`, `@shared/*`). No `../../..` crossing src boundaries.
- File naming: `kebab-case.ts` for modules, `PascalCase.tsx` for React components, `*.test.ts` next to the unit under test, Playwright specs under `e2e/`.
- Prettier and ESLint must pass (`pnpm lint`, `pnpm format`). Don't disable rules inline without a one-line `// reason:` comment.

## TypeScript discipline

- `strict: true` is non-negotiable. No `any`, no `as unknown as T`, no `// @ts-ignore` without a tracking issue link.
- Prefer `unknown` + a type guard over `any` at boundaries (IPC payloads, parsed JSON, file reads).
- Validate untrusted input with **Zod**: agent output, GitHub API responses, IPC payloads from the renderer, anything from disk that's user-editable.
- Discriminated unions for state machines (note status, draft status, agent run status). Switch on the discriminant; let TS exhaust the cases.
- Prefer `readonly` and `as const` for static data. Mutate locally; don't mutate inputs.
- Public functions exported from a module: explicit return types. Inferred types are fine for locals and React components.

## Architecture

- **Main vs renderer boundary is sacred.** The renderer never imports from `src/main/*`. Main never imports from `src/renderer/*`. Cross-cutting types live in `src/shared/`.
- **All IPC is typed and centralized.** Channels are declared once in `src/shared/ipc.ts` with request/response types. Handlers in `src/main/ipc/` register against that registry. Preload exposes a single `window.pilog` object — no raw `ipcRenderer` in the renderer.
- **Feature folders in the renderer.** UI lives under `src/renderer/src/features/<feature>/`. Cross-feature reuse goes through `components/ui/` (shadcn) or `lib/`. No deep imports across feature folders.
- Side effects (DB writes, network, FS, secret access) only in main-process service modules. Renderer code is presentation + IPC calls.
- Single responsibility per module. If a file exports more than one unrelated concern, split it.
- Composition over inheritance. No class hierarchies for domain logic; classes are reserved for things with intrinsic identity (e.g. a `WindowRegistry`).

## Data & persistence

- Schema lives in `src/main/db/schema.ts`. Migrations are generated by drizzle-kit into `drizzle/migrations/` and committed. Never hand-edit a generated migration; create a new one.
- Repositories (`src/main/db/repositories/*`) are the only modules that import the Drizzle client. Handlers and services depend on repositories, not on `db` directly.
- Timestamps stored as ISO 8601 strings (matches the data model in `docs/pilog_prd.md` §11). Generate them in repositories, not in callers.
- IDs are string ULIDs. Never expose autoincrement integers across the IPC boundary.
- A migration is required for every schema change touched in a PR. Reviewer should reject schema diffs that lack a migration file.

## Security

- GitHub tokens and any model-provider keys go through `src/main/security/secrets.ts`, which wraps Electron `safeStorage`. Never the SQLite DB, never plain JSON, never logs.
- The renderer never sees a token. If the renderer needs to perform an authenticated action, it asks main via IPC.
- `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true` where possible. New `BrowserWindow` calls that loosen these need an inline justification comment.
- Never `eval`, never `Function(string)`, never `shell: true` for child processes. Pass argv arrays.
- External URLs open via `shell.openExternal` after validating the scheme is `https:` or `http:`.
- Auto-publish to GitHub requires explicit per-repo opt-in (PRD §9.7) — code paths that publish must check the flag.

## Testing

- **Vitest** for unit tests. Every repository function, every IPC handler, every Zod schema, and every non-trivial pure function gets at least one test. Test names describe behavior: `"returns notes ordered by createdAt desc"`, not `"test1"`.
- Repository tests run against an in-memory `better-sqlite3` instance with the real migrations applied — not mocks.
- **Playwright** drives the packaged Electron build for end-to-end flows. Each phase in `docs/implementation-plan.md` lists its required e2e coverage; merge gates on those.

### Core Principle

Tests verify behavior through public interfaces, not implementation details. Code can change entirely; tests shouldn't break unless behavior changed.

### Good Tests

Integration-style tests that exercise real code paths through public APIs. They describe _what_ the system does, not _how_.

```typescript
// GOOD: Tests observable behavior through the public interface
test('createUser makes user retrievable', async () => {
  const user = await createUser({ name: 'Alice' })
  const retrieved = await getUser(user.id)
  expect(retrieved.name).toBe('Alice')
})
```

- Test behavior users/callers care about
- Use the public API only
- Survive internal refactors
- One logical assertion per test

### Bad Tests

```typescript
// BAD: Mocks internal collaborator, tests HOW not WHAT
test('checkout calls paymentService.process', async () => {
  const mockPayment = jest.mock(paymentService)
  await checkout(cart, payment)
  expect(mockPayment.process).toHaveBeenCalledWith(cart.total)
})

// BAD: Bypasses the interface to verify via database
test('createUser saves to database', async () => {
  await createUser({ name: 'Alice' })
  const row = await db.query('SELECT * FROM users WHERE name = ?', ['Alice'])
  expect(row).toBeDefined()
})
```

Red flags:

- Mocking internal collaborators (your own classes/modules)
- Testing private methods
- Asserting on call counts/order of internal calls
- Test breaks when refactoring without behavior change
- Test name describes HOW not WHAT
- Verifying through external means (e.g. querying a DB) instead of through the interface

### Mocking

Mock at **system boundaries** only:

- External APIs (payment, email, etc.)
- Time/randomness
- File system or databases when a real instance isn't practical

**Never mock your own classes/modules or internal collaborators.** If something is hard to test without mocking internals, redesign the interface.

Prefer SDK-style interfaces over generic fetchers at boundaries — each function is independently mockable with a single return shape, no conditional logic in test setup.

### TDD Workflow: Vertical Slices

Do NOT write all tests first, then all implementation. That produces tests that verify _imagined_ behavior and are insensitive to real changes.

Correct approach — one test, one implementation, repeat:

```
RED→GREEN: test1→impl1
RED→GREEN: test2→impl2
RED→GREEN: test3→impl3
```

Each test responds to what you learned from the previous cycle. Never refactor while RED — get to GREEN first.

## Errors & logging

- Main-process IPC handlers return a `Result<T, E>` discriminated union. Never throw across the IPC boundary; the renderer should see structured failures and surface them as toasts.
- User-facing errors are written for end users (no stack traces, no internal IDs). Log the technical detail to `app.getPath('logs')/pilog.log` via the shared logger.
- No `console.log` in committed code. Use the shared logger (`@main/lib/log`) so log destinations stay configurable.
- Catch the narrowest error you can handle. Re-throw or convert to a `Result` — never swallow.

## UI

- Tailwind CSS for styling. No inline `style` attributes except for genuinely dynamic values (computed dimensions, transforms).
- Use shadcn/ui primitives from `components/ui/` before reaching for a new dependency. If a primitive doesn't exist, generate it via the shadcn CLI rather than writing one from scratch.
- Lucide React for icons. No mixing icon libraries.
- Accessibility: every interactive element has a discernible label (text, `aria-label`, or `aria-labelledby`). Forms have associated `<label>` elements. Keyboard navigation works without a mouse.
- React: function components only. Hooks at the top of the component. No business logic in components — extract to hooks (`use*`) or to main-process services.
- State: local state via `useState`/`useReducer`. Cross-component server state via TanStack Query (added when needed) calling the IPC layer. No Redux in MVP.

## Commits & PRs

- Commits are small, focused, and the message says _what changed and why_, not _how_. The "how" is the diff.
- One concern per PR. If a refactor is needed to land a feature, do the refactor in a prior PR.
- Touching a PRD or implementation-plan section in code? Reference it in the PR description (e.g. _"implements `docs/implementation-plan.md` §3.1"_).
- Load-bearing decisions get an ADR in `docs/adr/` _before or with_ the implementing PR — not after.

## Interface Design

### Deep Modules

Prefer deep modules: small interface, deep implementation. A few methods with simple params hiding complex logic behind them.

Avoid shallow modules: large interface with many methods that just pass through to thin implementation. When designing, ask: can I reduce the number of methods? Can I simplify the parameters? Can I hide more complexity inside?

### Design for Testability

1. **Accept dependencies, don't create them** — pass external dependencies in rather than constructing them internally.
2. **Return results, don't produce side effects** — a function that returns a value is easier to test than one that mutates state.
3. **Small surface area** — fewer methods = fewer tests needed, fewer params = simpler test setup.
